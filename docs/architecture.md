# ground-control — Architecture

How the pieces fit: what tracks, what decides, what renders, and where a new agent, host, work source, or board plugs in. Requirements live in `prd.md`, measured mechanisms in `mechanics.md`, and the test contract in `testing.md`. This document also carries the stance the rest of the design leans on (§1).

Naming: the **hub** is the background process. `tracker` in the other docs means GitHub Projects, the team's work tracker; here that seam is the **work source**, and GitHub Projects is named in full.

## 1. Shape

One headless hub owns what every board needs to render and act: which issues the developer holds, which agent sessions are alive, what each session is doing, where each session is showing, and which lane the developer put each card in. Boards are clients of the hub. They render its snapshot and forward the developer's actions; they decide nothing.

```
                 ┌──────────────── hub (node, headless) ────────────────────┐
 work sources ──►│  poll · coalesce · watch activity · merge · lane memory  │──► snapshot + change events
 agent adapters ►│                                                          │◄── actions: refresh · move · open
 host adapters ─►│  one loop, one snapshot, one record of what is where     │
                 └──────────────────────────────────────────────────────────┘
                              ▲                                ▲
                   VS Code board (webview)          GitHub project overlay (Chrome, via a stdio bridge)
```

The hub is a single process per machine because two of the things it holds cannot be held twice. Lane placement is one record: a card in `Build` on one board is in `Build` on every board, or "a card sits in exactly one lane" (`prd.md` R8) is false. Hook installation is one act: two processes both syncing `~/.claude/settings.json` is the race the install lock exists to prevent.

A Chrome extension forces the hub out of VS Code. It cannot spawn `claude` or `gh`, read `~/.claude`, or watch a directory, so the tracking must run in a node process the browser reaches. Running that process inside a VS Code window would tie the browser board's lifetime to whichever window happened to host it, and elect a host among several windows on every launch.

The hub owns no work item's state. It reads what the sources report and what the developer placed; it never decides that a piece of work is done.

### Stance

- **Evidence over claims.** A session's phase comes from files the agent writes as it works, never from the agent's own report of what it did (`mechanics.md` §20; `prd.md` R23, R24). The hub never infers a phase from a transcript's age.
- **The control plane is authoritative; the project board is a projection.** When a `.factory/` control plane exists, its station state is what moves a card, and the GitHub Projects status becomes one more thing the board reads. Until then, the status and the developer's own placement are the only inputs.
- **Seize is stop-and-take-over, and it needs the editor.** Taking a session over stops it, hands it to the developer in an editor tab, and hands it back when the tab closes (`prd.md` R15, R17). Only an extension resident in the editor can do that; a browser board watches and moves cards, and sends a seize to the editor. Opening a session is not that: it stops nothing, so a browser board does it itself — by navigating to a `vscode://` link the extension answers, which is how focus is given rather than taken (`mechanics.md` §26, §29).
- **The tracking is headless.** Everything that reads the machine runs in the hub, so a board is only ever a renderer, and a second board is a second renderer.

## 2. The three seams

Every external thing the hub touches sits behind one of three interfaces, each backed by a registry in `packages/hub`. Adding a target is a new registry entry and a configuration id; nothing in the loop, the merge, the lane memory, or any client changes.

| Seam | Answers | Implementations |
| --- | --- | --- |
| **Agent adapter** | Which sessions are alive, what each is doing, what each is called, and — optionally — one bounded question answered as JSON, or one piece of work started in a checkout | `claude` |
| **Host adapter** | Where a session is showing, how to reveal it, how to release it | `vscode` |
| **Work source** | Which items are on the board, each one's status, and — optionally — one card's conversation | `github` |

### Agent adapter

One per agent CLI. It owns its transport, its response shape, where its transcripts live, the wording of its failures, and its activity signal.

```ts
interface AgentAdapter {
  readonly id: string;
  readonly displayName: string;
  readonly defaultPath: string;
  /** R30: whether this machine has the tool, read rather than spawned, so an absent one is never polled. */
  enabledByDefault(readers: MachineReaders): boolean;
  /** Every live session this CLI reports. Never throws; a failure comes back classified. */
  listSessions(path: string, deps: MachineDeps): Promise<{ sessions: Session[]; failure: ReadFailure | null }>;
  listHistory?(deps: MachineDeps): Promise<HistoryReading>;
  canResume?(session: HistoricalSession, deps: MachineDeps): boolean;
  /** The phase signal this CLI offers, or absent when it has none. */
  readonly activity?: ActivitySignal;
}

interface ActivitySignal {
  /** What to write to put the signal in place, or take it away. Pure: the hub does the file system. */
  plan(input: { settingsText: string | null; home: string; wanted: 'install' | 'remove' }): ActivityPlan;
  /** The agent's own settings file, which the plan is written into. */
  settingsPath(home: string): string;
  /** The directory whose changes mean a phase may have moved, watched by the hub. */
  watchDir(home: string): string;
  /** The last phase reported for a session, or null to claim nothing. */
  read(home: string, sessionId: string, readText: ReadText, now?: number): SessionActivity | null;
  /** A script the signal needs on disk, where it needs one. The hub writes it and never reads it. */
  readonly writer?: { path(home: string): string; source: string };
}
```

`MachineDeps` is the hub's view of the machine handed to every adapter: the `MachineReaders` (`readText`, `mtime`, `listDir`, `readHead`, `readTail`, `home`) plus the compiled branch pattern. `fetchSessions(config, adapters, readers)` in `core` compiles the pattern and fans out to the adapters named in the configuration; an unknown id is a named failure. An adapter never touches `node:fs` directly, which is what makes it testable against recorded reads.

`classify` and `dispatch` are the two things an adapter may offer beyond a roster, and they are opposites. A classification must leave no trace: no transcript, no settings, no tools, and a session the board filters out of its own roster (`mechanics.md` §31). A dispatch is the reverse — it writes a transcript, loads the developer's settings, works in their checkout and becomes an ordinary session on the card, because a process editing their code with nothing on screen saying so is the failure R2 exists to prevent. The caller cannot name that session: `claude --bg` mints its own id and prints it, so `dispatch` answers with the short id it read back and the hub resolves the full one off its next roster read (`mechanics.md` §33). `stopDispatch` takes it away again. Both are optional, and an agent that cannot start a session the board can later stop and hand over must not offer one — a run nobody can take back is worse than no automation (R15, R30).

`activity` is optional because the signal is the least portable part of an agent. Claude's is a hook script writing a marker per session (`mechanics.md` §20); another CLI may offer a status file, a socket, or nothing. An adapter with no signal produces sessions with `activity: null`, which the board already renders as no phase (R24).

**An adapter's roster may come from its own signal.** Claude reports liveness from its CLI and the phase from its hooks; Codex has no roster command at all, so the markers are both — `listSessions` lists the marker directory, and each marker carries the pid of the Codex process that wrote it, because a killed agent fires no end event and its marker outlives it (`mechanics.md` §39, §40). That is why `listSessions` takes a `path` it need not spawn and why liveness is the adapter's own business rather than a reader on `MachineDeps`: the transport an adapter uses to prove a session alive is as CLI-specific as the one it uses to list them.

`Session` is neutral. It carries what every board needs to place and label a card: `agent`, `sessionId`, `pid`, `title`, `cwd`, `checkoutRoot`, `branch`, `repository`, `issueNumber`, `startedAt`, `transcriptWrittenAt`, `activity`, and `finished`, the agent's own word that the session ended, which the lane rules read and never infer. Anything only one CLI reports goes in `details: Record<string, string>` for display, absent rather than null where the CLI said nothing. The board reads four keys where present: `name` and `shortId` in the label ladder after `title` (R11), and `state` or `status` as the CLI's own word when no phase is reported (R24). A field like Claude's background-session `status` never becomes a column every adapter has to fake, and `finished` is the only word promoted out of the bag, because a lane decision may not rest on one agent's vocabulary. `checkoutRoot` and `repository` come from the same upward walk that finds the branch, so the checkout a session belongs to is data every adapter reports rather than something a board infers from `cwd`: `mergeBoard` keys a card with no issue on repository and branch, and `checkoutOf` answers a live session's checkout root rather than the subdirectory it happened to start in. A card carrying only a saved session still answers with the directory that session recorded, which is all `HistoricalSession` holds.

### Historical sessions

An agent may implement `listHistory(MachineDeps)` alongside its live roster. `HistoricalSession` carries saved title, cwd, branch, issue number, canonical repository identity, and transcript modification time; it carries no pid, activity phase, or finished claim. `fetchSessionHistory` keeps history failures separate from roster failures. The hub reads history only after a complete successful roster read and serializes both reads, discarding results for replaced agent or pattern settings.

Claude scans parent transcript files under the injected home's `.claude/projects`, reading at most 64 KiB from each end. Parsed metadata is cached by absolute path and mtime. Every roster refresh discovers additions and deletions, including marker-triggered session transitions, visible-board refreshes, the session cadence, and manual refresh. Phase-only events do not scan history. The reader yields between projects, and unchanged files cost stats rather than repeated parsing; repository identity and issue-pattern matching are recomputed each scan. Incomplete filesystem reads report a history failure and publish no fallback. Missing metadata is skipped. The injected readers keep temporary-home tests isolated without process-global SDK settings.

`mergeBoard` excludes active `(agent, sessionId)` identities from history, deduplicates saved copies by newest modification time, then chooses one historical session for each existing issue card with no active sessions. Saved branches and directory names provide issue numbers; the checkout's origin remote (following worktree `commondir`) must match the issue URL's repository. Unknown remotes do not match. Ties use agent and session ID. An optional `lastSession` field carries this to both renderers, preserving older cached snapshots which omit it. It never enters live counts, activity processing, or lane decisions. The host includes supported historical IDs in `openable`; both boards send the same ID-only opening request for a reveal or resume. Stable historical rows remain visible during successful refreshes; just-ended sessions wait for fresh history, and unreadable rosters clear history immediately.

Historical opening refreshes the roster/history, then asks the agent's `canResume` to verify that the saved directory and transcript remain readable. The host receives validated `historicalSession` metadata alongside the live roster, and chooses `resume-here` or `resume-elsewhere` only if the session is still inactive. A standalone window on the saved directory may be reused; missing or multi-root targets use an explicit new window. The editor uses its own `out/cli.js` through `Code.exe` in Node mode, with argument arrays rather than shell interpolation.

The hub reserves historical resumes across clients before asynchronous window discovery. Each request retains ownership of its reservation; an old lookup cannot use or delete a newer click's reservation. Routes have a 30-second fire deadline within a 60-second reservation. The resident checks that deadline after its final fresh roster read, immediately before opening. Fresh roster requests queue behind in-flight reads instead of reusing a pre-history roster, and return null on incomplete reads. Landing verification recognizes the requested session's new process as expected. The reservation leaves time for it to register before another click may resume it.

### Host adapter

One per application a session can show in. It owns the host's persisted state, its window enumeration, and the verbs for reaching a session in it.

```ts
interface HostAdapter {
  readonly id: string;
  /** Parses this host's entry in the configuration, or names what is wrong with it. */
  configure(raw: unknown): ReadFailure | null;
  /** Warms whatever `windows` and `surfaces` read, once per session poll. */
  prime(deps: MachineReaders): void;
  /** Which windows are open, and which one is running this session. */
  windows(session: Session | undefined, deps: MachineReaders): Promise<HostWindows>;
  /** Which surface in which window holds each session, from the host's own records. */
  surfaces(deps: MachineReaders): Promise<SessionSurface[]>;
  /** A route to the session, or a named refusal with its remedy. Pure, and judged against this host's own settings. */
  plan(request: OpenRequest): OpenPlan;
  /** Which of these sessions this host offers to open. Another host's answer is its own (R14). */
  openable(sessions: readonly Session[], history?: readonly HistoricalSession[]): string[];
  /** Routes only a client resident in the host can perform, named so the hub can forward them. */
  readonly residentRoutes: readonly OpenRoute['route'][];
  /** Routes this adapter can perform from a headless process. Absent where every route is resident. */
  open?(route: OpenRoute, deps: MachineReaders): Promise<OpenOutcome>;
  /** Closes the surface holding a session so it can be handed back (§1, Seize). Absent where the host cannot. */
  release?(session: Session, deps: MachineReaders): Promise<void>;
}
```

A host adapter takes `MachineReaders` rather than the full `MachineDeps`: linking a branch to an issue is an agent's job, and a host never does it. Its own permissions stay inside it: whether the board may bring another window forward is R27's rule about one application's windows, so `configure` parses it and `plan` applies it, and the hub carries no setting whose meaning is a host's. Only a host the configuration names is reached at all: one left out of it was handed no settings, and an editor reached on defaults nobody chose reads another install's windows and brings the wrong one forward.

Two rules keep the seams from bleeding into each other.

**Placement knowledge lives in the host adapter, keyed by agent.** A session's location inside a host is recorded by that agent's integration with the host: a Claude tab in VS Code is a webview with `providedId` `claudeVSCodePanel` holding a session id in its own state, and a Claude window announces itself in `~/.claude/ide/<port>.lock` (`mechanics.md` §21, §22). A Codex thread is not a webview holding an id — it is an editor resource, `openai-codex://route/local/<id>`, and the tab's own URI is what names the thread (§44). So a placement row carries how a tab says which session it holds, as one of two shapes: a key inside the webview's state, or a scheme and a path prefix on the tab's resource. It carries the reveal the same way — a command and the arguments it takes — because Claude's takes a session id and Codex's is VS Code's own `vscode.open` on that URI.

Two consequences of that difference are the host's to hold. A Codex reveal is idempotent, so a second one re-activates the tab where Claude's forks a surface (§6); and Codex's sidebar records nothing, so no record ever names the surface holding a thread the developer left there — where Claude's sidebar carries its session id. That is what an idempotent reveal buys. Where no record names the surface, a reveal that names the session is fired at the window anyway, because there is no guess in it to get wrong — which is the only way a thread the sidebar holds is reached at all. Which window is a separate question, answered by the session's own process: a Codex thread runs inside the `codex app-server` its extension spawns per window, so the pid walk that names a Claude window names a Codex one (`mechanics.md` §47). The executable that pid belongs to is a placement row's, like every other identifier the host reads an agent by. The `vscode` host adapter holds `PLACEMENTS`, a table per agent id of the webview id, the sidebar memento keys, the state key carrying the session id, the lock directory, the process name, the extension id, whether the reveal is idempotent, the reveal and focus commands, and the open URI, because the host owns the storage format and the agent owns the identifiers. A session whose agent has no row is refused by name. An agent adapter knows nothing about any host.

**Not everything in a host package is a member of the adapter.** `HostAdapter` is what the hub calls, and the hub reaches nothing that needs an editor of its own. Showing a card's changes is decided in `host-vscode` because the rules are VS Code's — how a multi-diff editor is addressed, which repository a command would resolve to — but no hub asks for it, so it is a pure function beside the adapter rather than a verb on it: `changesPlan` follows each file through the three ranges Git answers separately (`mechanics.md` §30) into one row spanning all of them, and `repositoryRefusal` decides whether the repository VS Code answered with is the one the card names. The extension fetches and opens; both halves of the decision are vitest's.

That refusal exists because the failure it catches is silent. A `{repository: true}` command resolves its argument by longest open-repository root prefix and, on a miss, hands back the window's only repository without prompting (`mechanics.md` §30) — so a worktree that failed to open would have the main clone diffed under the card's name. The board compares roots itself and runs nothing until they match. For the same reason the base is `getMergeBase` over the remote's default branch rather than `getBranchBase`, which answers in one call but writes `branch.<name>.vscode-merge-base` into the checkout's config: looking at work must not change it.

**A host adapter has a headless half and, where needed, a resident half.** Locating a session is reachable from the hub. Reaching it is not always: every route into VS Code that fires a URI or a command must first confirm that the target window has focus, because the URI follows focus and a miss starts a fresh agent in the wrong window (`mechanics.md` §7, §8), and a headless process has no focus signal. So today every `vscode` route is resident, and the adapter offers no `open` at all rather than one that performs nothing. The adapter names such routes in `residentRoutes`; a client that can perform them says so when it connects, and the hub forwards those actions to it. A host with no resident half, such as a terminal, lists none, and its `plan` never returns one.

`release` over a window's own port is unbuilt, so the `vscode` adapter omits it too. Closing the surface costs the window its IDE connection (`mechanics.md` §22), and until §22 characterizes what reopening one costs, no host performs a release. Both verbs are optional on the interface rather than stubs, so a host cannot claim a capability it does not have.

### Work source

One per place work items come from. `github` reads the developer's assigned issues through `gh` and reports the GitHub Projects status that decides whether a card is on the board and where it arrives (`prd.md` R8, R9). The `.factory/` control plane becomes a second source when stations exist, and station state then becomes the second thing that may move a card.

```ts
interface WorkSource {
  readonly id: string;
  readonly displayName: string;
  /** Takes this source's entry in the configuration and holds it, or names why it will not read with it. */
  configure(raw: unknown): ReadFailure | null;
  read(): Promise<SourceReading>;
  /** One item by number, keyed by `repositoryKey`. Optional; a source that cannot serve one answers with nothing. */
  readCard?(repository: string, number: number): Promise<CardReading>;
}
```

A source holds the last configuration it accepted, and a refused one leaves it holding nothing: reading with the settings from before a refusal is reading with settings nobody set, under a board that already says the settings were refused. So `SourceReading` is three nullable fields rather than a result, and the two ways of reading nothing are told apart. `items` null beside a `failure` is a read that failed, and keeps whatever the source last returned on the board (R24). All three null is a source with nothing to say at all, and its cards go: they were read for a repository the developer is no longer asking about.

`readCard` is the one read that is not about the developer's own work: a session names an issue by branch, and the assigned read by definition never returns one that has been handed on. It answers `{ card: null, failure: null }` for a repository it does not serve, which is how the GitHub source refuses a number read off some other checkout's branch — its setting is a bare `owner/name` against github.com, so an Enterprise clone matches nothing and its sessions stay ad-hoc. A `null` card with no failure is never an error: it is the board declining to name work it cannot establish.

`needs` is what a source can work out for itself but may not adopt. GitHub reads the logged-in accounts out of `gh auth status`; every query it makes is `assignee:`, and picking one would put somebody else's issues on the board as the developer's. So it reports them as detected, reads nothing, and a client puts the question to the developer (R26, R28).

`WorkItems` carries the cards, the counts R1 asks to be stated, and `owners` — who the read was actually made for, which the lane rules use to tell the developer's own pull request from a colleague's. That is a read of the source, not of the setting, so a login the developer has just typed does not change how cards are laned until the read that used it lands.

The hub reads the sources its configuration names and no others, so a source in the registry that nobody asked for costs nothing. A source the configuration stops naming, and one whose settings it refuses, both lose their last read the moment that configuration lands rather than at the next poll: with nothing watching there may not be one, and cards read for settings nobody is naming any more would sit on the board for the length of a poll interval. A board with a source it cannot read is stale and dims, whether the read failed or the settings for it were refused — a misconfigured host is worth saying and is not staleness, because the cards on screen are still what the world says.

Every source's last read merges into one board, and the items' `fetchedAt` is the oldest of them: the board is only as fresh as the source that has not been read since. A source that throws rather than returning a failure is named on the board like one that failed — the seam is public, and a rejection swallowed would take the whole pass's broadcast with it and say nothing anywhere the developer looks.

## 3. The hub

The hub is the loop that was the board panel's, made headless and made one per machine.

- **Two cadences and a tick.** Work sources are a network round trip and poll on the long interval. Agent adapters spawn a CLI and poll on the short one. Each source keeps its last good read and its last failure, so one failing never blanks another. Under both runs a fixed five-second tick, which polls nothing itself and costs nothing on the passes that find nothing to do. It exists for the two things a cadence cannot answer for: a machine that was suspended, and a source that has come back.
- **A suspend is a gap, and a gap is read now.** Both readings come out of a sleep as old as the sleep was, so waiting for the next interval would leave a laptop opened after an hour showing an hour-old board. A tick that fires more than twenty seconds after it was due is a machine that was off rather than a loop under load, and it reads the work sources and the agents at once. An outage nobody has been told about gets its minute over again, because the network is not up the instant the lid is: one that the board has already stated stays stated, since a stall long enough to look like a suspend must not retract a notice whose condition still holds.
- **A network that is not back yet is ridden out, not reported.** An adapter marks a failure transient when nothing anybody does will fix it — `gh` reporting that it could not reach api.github.com is the shape this exists for. The board keeps the read it already has and says nothing for a minute, retrying every five seconds while the outage could still be a blip, then every fifteen, every minute past two minutes, and every two minutes past ten. The ladder is stepped by how long the source has been unreachable rather than by how many tries it has cost, so a developer pressing refresh cannot spend it and leave the board recovering later than if they had left it alone. It still dims and still says it could not refresh, because R24 forbids implying a read succeeded, and a source with no read behind it is stated at once rather than ridden out — an empty board owes its reason. Past the minute the failure is named above the lanes like any other, broadcast by the tick rather than left waiting on the next try, which may be two minutes out. What it asks for is to wait: a board that is already retrying is not something to press a button at.
- **Every read carries a deadline.** Thirty seconds a page for the poll, twenty for one card's triage. A blackholed network — a captive portal, a link dropped mid-request — otherwise hangs a read for the life of the hub, and every later refresh coalesces onto that one rather than starting its own, so the board never comes back at all. A read that runs out of time is transient like one that could not connect: the deadline is short enough that hitting it is a slow network far more often than it is a broken query, and what the board would say about it is the same either way.
- **Activity is event-driven.** The hub watches each activity signal's directory. A change on a listed session is one marker read; a marker removed, or one naming an unlisted session, is a roster change that only the CLI can settle, so it triggers a session read. Changes batch for 150 ms. The directory comes and goes with the install and `node:fs.watch` cannot be armed on a missing path, so the watcher re-arms until it appears and again whenever it is removed underneath. A marker's kind is decided from one `exists` on that path against the set the watcher held before the batch: a listing taken mid-batch already holds markers whose own events have not arrived, which would read every one of them as a rewrite.
- **A floor per cost.** A read in flight absorbs a timer or a button, and a change that read cannot have seen queues one more behind it: an activity event for the sessions, and for the sources a configuration whose settings moved, because the read in flight went out with the ones it replaced. Beyond that each read waits out the floor its own cost earns. A session read spawns a CLI, so two asks within a second are one read. A source read is a network round trip, and a board reports itself watching on every tab switch and the browser worker on every restart Chrome puts it through — so a reading less than a minute old is what a board becoming visible is shown, where reading for each of those would ask GitHub once a second and be rate limited. A read asked for waits out the second, not the minute: the timers ask, so a cadence set below the floor is still the cadence, and so do the refresh button and a configuration whose source settings differ from the one being polled with. Settings restated unchanged — which every board that opens does — ask for nothing. The comparison is order-insensitive, because a source's entry is a shape `core` does not know and a client may build it in any order.
- **Idle when unwatched.** A client says whether it is watching: the VS Code panel reports hidden, and the Chrome bridge disconnects when no project-board tab exists. With no client watching, the hub stops polling and an activity event costs nothing. Timers are rebuilt only when the watched state or a cadence changes: a client that says what it already said — a browser worker Chrome restarted, a second board arriving — would otherwise restart the clock the periodic read is counting on. Each session poll costs about a fifth of a second of CLI time (`mechanics.md` §2), which nobody would be looking at. The hub exits after 30 minutes at zero clients, and the next board open starts it again in about a second. A window that has activated the extension stays connected whether or not a board is open, because a setting changed with no board on screen still has to reach it (R34).
- **It writes down what it is doing, and a client may ask to watch.** `hub.log` holds a line per source read with its duration and its count, per `gh` invocation, per client arriving and going, per card moved, per configuration the hub took or refused, and per run the board starts, stops or settles. Each line is a timestamp, a level, an optional bracketed scope and a sentence. The scope is bracketed rather than punctuated, and is one lowercase word, because the file is read back: half the hub's own messages carry a colon, and several carry a CLI's own output, which opens with a bracket often enough to matter. The floor rides the configuration like any other setting, and stops at `info`: above it a stored setting would silence the hub coming up, the hub stopping, and every refused request, and a client whose hub will not start sends the developer to that file to find out why. `debug` adds a line per `gh` call, per session read and per marker batch — off by default because it is noise in a file whose reader has usually opened it after something went wrong, not because of what it costs. A condition that persists is written once rather than per read, keyed on the subject and the kind of the failure and never on its message: an agent adapter puts its CLI's own words in one, and a message that moves between attempts would defeat the very thing the rule is for. The spawn points the hub's own stdout and stderr at the same descriptor, so the file also holds lines no logger wrote — a crash, and the banner a foreground run prints — which is why anything that does not parse is kept verbatim under the timestamp of the line above it: that is what puts a stack trace under the error it belongs to, and those are the lines a developer opening the log after a crash came for.
- **Nothing about the log crosses to a client that has not asked.** A viewer opening sends `watchLog`, and until one does the hub holds no subscriber, reads no file and sends nothing. Opening is answered with the tail of `hub.log` and then a message per line as it is written. The backfill comes off disk rather than out of a ring buffer the hub would have to keep against the chance somebody looks — the file is written whatever happens, so the buffer would be a second copy of it — and reading it that way is also what lets a viewer opened after a restart carry the previous hub's dying words. A truncated read opens mid-line, so its first line is dropped. Watching the log never makes a client watched: a developer reading it is not a board on screen, and turning the poll loop on for one would spend a CLI spawn every thirty seconds for a window nobody is looking at (R35).
- **Lane memory is a file.** `~/.claude/ground-control/lanes.json`, written atomically, read by every client through the snapshot. A client never stores placement of its own.
- **Triage is the same shape, and it labels rather than moves.** `~/.claude/ground-control/triage.json` holds what the board has read each card to be asking for, re-read from disk on every access the way the lane store is. A card is due when it has no reading, when its reading belongs to a pass past the developer's hands that has ended, or when its status has moved since — and an archived card is never due, which is what keeps a rule about absence from being a loop over cards that sit archived in every snapshot.
- **What marks a reading out of date is separate from what re-reads it, and both are evidence.** An entry stores `evidenceOf` — the issue's timestamp and status, and the pull request's number, state, timestamp, head commit and check rollup — and a card reads stale when that string no longer matches. The pull request's own three are there because GitHub does not touch the issue when somebody comments on its pull request, pushes to it, or when a build goes red under it (`mechanics.md` §48); the rollup is stored as red-or-not, so a card does not go stale for the length of every build. `reviewDecision` is in neither the evidence nor the classifier's prompt: it lags the team's own decision, and a review submission moves the pull request's timestamp anyway. Nothing ages out — a reading nobody has contradicted stays current however old it is, and the age is shown as a fact rather than as a verdict (`prd.md` R24). Readings run two at a time, behind one budget covering the source read and the classification together, and only while a client is watching: an editor window stays connected with no board open, and an unwatched hub must not spend. Nothing about it touches a lane.
- **Issue titles outlive the assignment, in a file.** `~/.claude/ground-control/issues.json` holds every issue the board has read by `<repositoryKey>#<number>`, written on each source read while the issue is still assigned. That is what makes the ordinary case free: by the time the assigned search stops returning an issue a session is still open on, the title is already on disk, and an offline board is missing nothing. Only what a session still names or a read touched in the last thirty days is kept, and only a card whose content actually changed is written — the comparison is order-insensitive, because a card reaches the file out of a source in one key order and back out of the parser in another, and what decides whether to write is the text. Any reading stands six hours: a number that named nothing may have an issue filed against it since, and a card nothing refreshes once the developer is unassigned would otherwise go on naming a status the issue left weeks ago. The stale one still answers while it is taken again, so no card blanks. A number the store has never seen costs one `readCard`, at most one in flight per key, and the session keeps its checkout card until it lands, so no card is ever bare.
- **Nothing is looked up until a source has read.** Sessions come off local disk and land before the first `gh` round trip every time. An empty card list read as “none of these are assigned” would archive the developer's whole board, and archiving is what costs a card the lane it was placed in — so both the lookup and the merge treat “no source has read yet” as knowing nothing, never as knowing the answer is none (R8, R24).
- **A read that failed and a repository nobody serves are different answers.** A source answers `null` to say it does not serve a repository — a number read off a branch in some other checkout — and that is not written down: recorded as “no such issue” it would leave a hub started before its settings arrived claiming the developer's own cards do not exist. Only a source that served the read and found nothing writes that. A failure writes nothing either, and holds the key off for five minutes, because the session poll would otherwise put a `gh` process up for it twice a minute for the length of an outage. Three reads at once at most; the rest come round on the next pass, and nothing on screen is waiting on any one of them.
- **A reading carries two clocks, because only one of them costs money.** An entry records what the card looked like when it was read and, separately, when its status last moved. The first ages the label and is free; the second makes the card due again and spends a model call, so it keys on the one change that is an instruction rather than on everything that moves a card (R38). The status timestamp rides the board query every refresh already makes (`mechanics.md` §32), so nothing is fetched to decide whether anything needs fetching.
- **Triage is deterministic first and a model second.** A work source reports what happened to a card — status moves and assignments, as GitHub recorded them — and `packages/board` decides what a run of them means: which writes were one act, what the card was last told to be, and which comments that instruction has already answered rather than left open. Where the status or the pull request settles the action, the model is handed it and asked only for the sentence; where they do not, it chooses among the actions as before. The split is what makes the label testable: the judgement lives in pure functions over a recorded timeline, and the model is left the one field only it can write.
- **What a run is for is the card's reading, and the board derives no merge of its own.** GitHub's mergeability is never fetched: a branch quietly falling behind is not an instruction to touch it, and a branch that will not merge is another team's job here. So the one automatable action arrives the way every judgement does — from what people wrote on the card, or the developer's own press — and `packages/automation` decides only whether the board *may* act on it. `derivedAction` is left one fact, `fix-checks`, which still outranks the model.
- **Acting is triage's shape again, and it moves nothing either.** `~/.claude/ground-control/actions.json` holds what the board has run on each card, read from disk on every access like the other two. The stored reading is what makes a card a *candidate* and what says which action it wants; what authorises a run is a fresh read of the pull request taken immediately before dispatch, because a label may be twelve hours old and this one pushes code — the read supplies the branches, the base and the head commit, never a second opinion about whether a merge is due. A refusal the board reached on its own is named and stored, so the same read is not made again next pass; one the developer asked for is answered to their board instead, because storing it would close the read gate on their own next attempt. Both a run and a stored refusal close that gate for half an hour — without it a board of fifteen cards would ask GitHub about each of them every loop. A run is never made twice against the same evidence, which is the head commit: one run per push, so a merge that stopped short is not started over forever and a push makes the card eligible again. The head is the branch's own state and nobody else's — authorising against the base would spend a run every time somebody else landed something. A run that landed blocks whatever the evidence then says, because the push it made is what moved the head: comparing evidence alone would have every success authorise the next one. A dispatch that never started a session is exempt, because nothing was spent, and a stored refusal carries the revision that wrote it, so a bump clears a reason a retired gate left on a card nothing reconsiders.

Three things bound what a mistake can cost, and all three live in one file — which is why a write to it that fails stands the runner down rather than being ignored: the run record that says a card is being worked on, the read gate, and the ledger the daily ceiling counts. A board that carried on without them would have no ceilings at all. The concurrency ceiling is counted from the runs the board is following rather than from the dispatches it is making, because `--bg` returns in milliseconds and starting one broadcasts, which considers again.

A finished run's outcome is read from the file the run was handed, and GitHub is not asked again: the base branch moves within minutes of a merge, so a conflict somebody else landed afterwards would read as this run having failed and an untouched branch as fine. Only the session knows whether it finished, and silence reads as stopped short — the last run's copy of that file is cleared before a new one starts, and a board that cannot clear it starts nothing. That advances nothing (R23): no lane, no status, no placement, just a sentence on a chip over a session the developer can open. Nothing about it touches a lane, it settles what is in flight before it prunes — a run still working is kept whatever became of its card, or the developer loses the control that stops it — and it never acts on a roster it has not read, because the first source read of a hub's life lands while the roster is still empty and every card then looks like a card nothing is working on.
- **Activity install is the hub's, and it follows the configuration.** It applies each agent's `ActivityPlan` under the existing install lock and reports what it observed, never what it intended (R25). An install reaches the agents the configuration names and leaves every other one untouched, because writing into the settings of a CLI the developer never asked the board to read is the board's own doing (R30) — and because taking entries out as a side effect of a settings edit would make one typo in that list strip a working agent's hooks. What removes them is the developer turning the hooks off, or an uninstall; both reach every agent, so nothing is left firing a writer nobody maintains (R34). Each agent's backups are named for it and kept per agent, since two of them write different files. The install and announce marks live in `hub-marks.json`; the announce is per client, so a second window still sees the notice once.
- **The hub owns the defaults, and remembers what it was told.** Its configuration is built from each adapter's `defaultPath` and what its `enabledByDefault` finds on the machine (R30) plus the shipped statuses and lanes (R27). A client pushes its settings on connect and on every change. The hub writes each configuration it accepts to `~/.claude/ground-control/config.json` and starts on that, because a default is not enough for every source: which repository work is tracked in cannot be guessed, and the settings that say so live in an editor that need not be open — so a hub the browser started would otherwise report itself unconfigured however long ago the developer set it (R36). A refused configuration is never remembered, or the mistake would outlive the window that made it. The file is parsed on the way back in exactly as a pushed one is: one field of it becomes a process, and it sits in a directory any process running as the developer can write. Every registered host and source is named in the defaults with an empty entry: a source nobody has configured then says what it is missing, where saying nothing would read as a developer with no work assigned to them. Every setting that reaches the hub is application-scoped in VS Code: one board's memory is shared by every window (R9), so two windows can never disagree.

### Protocol

The snapshot and the actions are one typed contract in `packages/core`, and every client builds its messages from those types. A field renamed in the hub fails the typecheck in every client rather than rendering an empty board (`testing.md`, "The webview protocol is typed on both sides"). The protocol carries an integer version; a client and a hub that disagree on it do not talk.

| Direction | Message | Carries |
| --- | --- | --- |
| client → hub | `hello` | client id, the host it lives in or none, its workspace root, the resident routes it can perform, whether it is watching |
| client → hub | `configure` | the client's settings, merged over the hub's defaults, and whether the developer asked to be told what the activity install did |
| client → hub | `watching` | whether the client is looking at the board now |
| client → hub | `refresh` | — |
| client → hub | `move` | card key, lane id |
| client → hub | `open` | session id, and whether the agent's own extension is ready — read on the click, because an extension activates while a board is up |
| client → hub | `retriage` | card key. The one message that spends money, so the hub checks the key names a card on the board and rations the ask |
| client → hub | `runAction` | card key. The message that changes the developer's code: every gate an automatic dispatch runs is run for this one too, against a fresh read. What the click replaces is the setting, never a safety check |
| client → hub | `stopAction` | card key. Stops the session the board started on it, and nothing else about the card |
| client → hub | `watchLog` | whether this client has a log viewer open. Nothing about the log reaches a client that has not sent it |
| hub → client | `snapshot` | lanes, per-source counts and failures, which sessions are openable, the hook notice, what the hub needs from the developer, when it was read |
| hub → client | `changed` | the same, sent on any change; clients replace, never patch |
| hub → client | `perform` | a resident route, forwarded to the one client that offered it |
| hub → client | `notice` | a message for the developer, with the refusal it came from where there is one |
| hub → client | `log` | log entries, only ever to a client that asked. The first carries the tail of `hub.log`; each one after it carries the line just written |

A third direction lives in the same file: `BoardMessage`, what an editor board's panel posts into its own webview. It is here rather than in the extension because the panel and the webview script are different languages in different processes, and a field renamed on one side of a hand-written literal is silent — it renders a board with a dead control. The webview answers with a `ready` once per run of its script, which is the only signal it has reloaded.
| bridge → browser | `trouble` | that the hub is not answering, or that it is again — the bridge's own, since a client cannot be told by a hub it cannot reach |

A configuration is parsed before it is taken, and a bad one is refused whole and named above the lanes rather than half-applied: one field of it becomes a process, and a client is not necessarily this editor. What it settled on is broadcast before the read it triggers, because that read has a floor: a setting corrected within a second of being made wrong would otherwise leave every board showing the complaint until the next poll. A client restates its configuration after every `hello`, since a hub it has just started knows nothing about it.

**Two messages are restated after every `hello` and neither is ever queued**: the configuration, and `watchLog`. A hub a client has just started knows nothing about it, and one that restarted under a reconnect holds neither the settings nor the log subscriber it held before. Queuing either instead would land it behind the restated copy — a configuration held over a reconnect is by then the settings of some earlier minute, and a second `watchLog` would have the hub re-read and re-send a tail the viewer has already been shown. That is a rule the transport enforces on both of its queue paths, and one every client owes an `afterHello` for: the bridge has no configuration to restate but does have the subscription, and a hub is replaced on every VS Code window reload, so a browser sidebar without it would show the lines from before the restart and never another.

`needs` on the snapshot is what the hub cannot detect and must ask for once, in place (R26): today, the developer's GitHub logins when none are configured. The client that can ask does, saves the answer to settings, and pushes `configure`.

### Transport

The hub serves HTTP on `127.0.0.1` on an ephemeral port: the snapshot and the actions as requests, changes as Server-Sent Events with a comment heartbeat every 20 s. Every client reaches it the same way, whether it is a VS Code window or the Chrome bridge.

| Route | Carries |
| --- | --- |
| `GET /hub` | the hub's name, protocol version, a fingerprint of its configuration directory, and, when the caller supplies a nonce, an HMAC of that nonce under the token. No token, and nothing else — not the pid, not the version of the code |
| `GET /snapshot` | the snapshot as it stands |
| `GET /roster` | a fresh read of the sessions on the machine, for a client carrying out an open route |
| `GET /events?client=<id>` | that client's stream: `snapshot`, `changed`, `perform`, `notice`, `log` once it has asked, and a `: ping` comment every 20 s |
| `POST /actions?client=<id>` | one `ClientMessage`. `hello` is the first, and it must name the client its stream belongs to |
| `POST /shutdown` | the stop |

A client reads `~/.claude/ground-control/hub.json` for the port and the token, then probes `GET /hub` with a fresh nonce and sends the token only to a listener that answers as a hub, for the same home, on the same protocol, holding the same token. The fingerprint alone would not do: it is a hash of the home directory's path, which any process running on the machine can guess, so on its own it lets anything holding the port be believed. The proof is what the record's own token is checked against, and it never puts the token on the wire. Liveness is that probe, never the file's existence; a stale `hub.json` is the normal state after a hub is killed, not an error (`mechanics.md` §25). A stream is what a client is: an action for a client with no open stream is refused, and a stream that closes disconnects it, which is what makes "nobody is connected" something the hub can tell.

The transport narrates itself through a callback its client supplies, levelled: the connect, the retries and the outage at `info`, and the line per message at `debug`. It is a callback rather than a logger because where those lines go is the client's own business — a VS Code window writes them to an output channel, and the bridge, having no channel, relays them to the browser as the browser board's own half.

The server refuses any request carrying an `Origin` header, any `Host` other than its own loopback address, any target that is not origin-form, any `POST` that is not `application/json`, any body over 64 KB, and more than eight event streams. A web page can reach loopback, and the request that pushes configuration carries executable paths, so nothing a browser can send is accepted. The browser board is reached another way. The first three happen before any route, and each is written to `hub.log` with the header that decided it while the client is told only that it was turned away. Those three are the ones worth recording: a client refused by them sees a status it cannot tell from a port some other program has taken, so without the hub's own note a board that cannot reach the hub it can see leaves no evidence anywhere on the machine. The rest refuse a request that already reached its route, which the client asked for and can read from the answer.

**The Chrome bridge.** Chrome talks to the hub through native messaging: a per-user host registered under the developer's own profile (`HKCU` on Windows, the profile directory elsewhere), which Chrome starts on demand and talks to over stdio. The bridge is the hub bundle in a second mode. It reads `hub.json`, starts a hub if none answers, connects to the event stream with the token, and relays messages both ways. It connects as a client with no host and no resident routes, so no route is ever forwarded to it.

The bridge is the boundary the browser is held at, and it is a whitelist rather than a blacklist: `refresh`, `watching`, `watchLog`, and a `move` to a lane the board has, and everything else is refused by name and the refusal sent back for the overlay to show. It is also the one place that edits what the hub sends back, taking the origin out of a refused-request line before the browser sees it. Going to a session does not widen it: that is a navigation the browser makes, answered by the extension's own URI handler, and it never passes through here. `runAction` and `stopAction` are refused in their own words rather than by the catch-all, because they are the messages that would have a web page start an agent in the developer's checkout. The hub's own server treats it like any other client, so the rule has to live where the browser's messages arrive. Frames are Chrome's own: four bytes of length and then JSON, reassembled across however stdin chunks them, with a header claiming more than a megabyte treated as a stream out of step with its frames rather than a body to wait for.

Google Chrome is the browser it registers with: the manifest goes where Chrome looks for it, and on Windows under Chrome's own key. Chromium, Edge and the rest read their own locations and would each need a row; none has been asked for.

The registration is written by a deliberate command, **Ground Control: Enable GitHub Overlay**, removed by the command that reverses it, and removed again when the extension is uninstalled — what it names is the bundle the uninstall deletes, so left behind it would have Chrome starting a host that is not there (R34). What it writes is a wrapper script and a manifest naming it, plus the registry value Chrome finds the manifest by on Windows. The wrapper prints nothing of its own: Chrome reads the process's stdout as message frames, so a line from a shell is a malformed frame and the port closes. It names the bundle at `~/.claude/ground-control/hub.js`, never the copy inside an extension, so an update never orphans it.

### Lifecycle

The extension writes the hub bundle to `~/.claude/ground-control/hub.js` on activation when the version it carries is newer than the one on disk, and never when older, the way it writes the hook script. Each copy carries its version on its first line, so which is newer is read without running either. Equal versions compare bytes, which is the case every development build hits — every build in a source tree carries the same version, and without that rule a rebuilt hub would never reach the disk. A bundle that cannot be written is said out loud and nothing else in the window is lost: the hub already on disk from an earlier run still starts.

The bundle is compared against the hub that is running, not only against the file: a hub whose record was written before the bundle was is running an older copy, and the client that finds it stops that hub — by the record it found, never by the file read again, because a replacement may hold the record by then — and starts what is on disk now. Both sides of that comparison are file times from the one filesystem, the bundle against the `hub.json` its hub wrote as it bound, because a time read on one clock cannot be compared against a time read on another. That is what a rebuilt bundle takes to reach a board — a build and a client, rather than a `--stop` by hand — and it is how a fix shipped in an update reaches a machine at all. A client with no starts left in its budget stops nothing, because a stop it has nothing to follow with would leave the board with nothing; a stop that hit nothing is a hub already replaced, and the client takes whichever one answers now. The cost is that a bundle which will not run takes the board down with it, where an unreplaceable hub merely went stale — the client says which of the two happened, and that is the trade the rule is worth.

The spawn command, the native-messaging manifest, and the uninstall all point at that one path, so an extension update never orphans a running hub.

A client starts the hub when `GET /hub` does not answer. VS Code spawns its own executable as node (`ELECTRON_RUN_AS_NODE`, the Node measured in `mechanics.md` §21), detached and unreferenced so it outlives the window, with output appended to `hub.log`. There is no search for an interpreter: the extension host's PATH is the launcher's rather than the shell's, and the Electron it is already running is the one Node that is certainly there. A child spawned that way survives the editor closing (`mechanics.md` §26), which is what lets the browser overlay keep working after VS Code is gone.

The hub scrubs `ELECTRON_*`, `VSCODE_*`, and `NODE_OPTIONS` from its own environment at startup. Not for the `code` CLI's sake — that sets `ELECTRON_RUN_AS_NODE` itself and clears it before launching the app (`mechanics.md` §26) — but because `VSCODE_IPC_HOOK` names the pipe of the window that started the hub, and every CLI the hub spawns would inherit it.

Single instance is the record, not the socket: `listen(0)` cannot collide, so binding decides nothing. A hub probes the recorded port before binding, and afterwards claims `hub.json` by exclusive create; the one that loses that create closes and stands down, and a record naming a port that answers as nothing is a hub that was killed and is taken over. Only a hub whose own pid is still in the record ever removes it, so an orphan cannot take the winner's record away with it. A client talks only to a hub on its own protocol. One answering a different number is a hub, but not one it can speak to, and which of them gives way is the same rule the bundle follows: newer wins. A newer client stops the older hub over `/shutdown` — the record's token proves it is the developer's own, and stopping is one route in every version — and starts its own. An older client stops nothing and starts nothing, because the bundle it would run is the newer hub's; it says so and asks to be updated. A cold start of the bundle costs 60 ms (`mechanics.md` §26).

What `GET /hub` answers is the one shape that must survive every version: a client that cannot parse it cannot tell an older hub from a stranger on the port, and would tell the developer to stop a hub that is theirs. Fields may be added to it; the three it has are fixed.

Seven things come to the same nothing at a client: no record, a port nothing holds, a port that went quiet, something that is not a hub, a hub tracking another home, a hub whose token this record cannot prove, and a hub of another protocol. Only the first is "there is no hub". Every other one is a process that is up and did not become this client's hub — and the hub the client then spawns stands down against it. It names the port and, where the record describes the process holding it, the pid; the remedy is ending that process, because a hub whose token this client could not prove cannot be told to stop — `/shutdown` needs that token. Where the miss is that something answered as not a hub, the client says what it answered — the status and the first line of the body, clipped to one — because the alternative is telling a developer that a stranger holds a port on no evidence, and that answer is the only evidence there is. A probe that goes quiet is asked once more with three seconds rather than half of one, because that deadline is spent on the client's own event loop: a window that has just activated is not a hub that is gone, and treating it as one is how a board comes to start a second hub against a working one.

A spawn that stands down writes why into `hub-exit.json`, the same file an orderly stop writes. Without it a spawn that found the home already served and a spawn that died are the same silence to the client that asked for one, and the client would tell a developer to go stop a stranger while their own hub is up and only that window cannot see it. What the client says instead names the running hub's port and that it is the one it cannot reach.

A client that cannot reach its hub retries with a doubling backoff from one second to thirty, starting one again each time none answers. What bounds that is a budget on **consecutive** starts that never answered: one a minute, three in five minutes, and then the developer is told, with the reason the last hub stopped and the path of its log. The budget is one client's, not the machine's — two windows each hold their own, which is what keeps a window's own retries paced without one window's trouble silencing another's board. A start that produced a live hub clears the count, so killing a working hub gets it back at once rather than after a minute — only a hub that will not come up at all is one the board stops making.

There is no orderly signal on Windows for a process without a console (`mechanics.md` §25), so the stop is `POST /shutdown` with the token, or `ground-control-hub --stop`, which does the same over the same route. An orderly stop removes `hub.json` and writes `hub-exit.json` with the reason; a hub that was killed leaves the first behind and never writes the second, which is what a client whose spawn did not come up has to go on. Uninstalling the extension shuts the hub down, removes the activity hooks and the Chrome registration, and removes the bundle.

### Privacy

**Board state and interaction are local. Classification is not.** Everything the board reads, remembers and renders stays on this machine, and nothing about the developer's work is sent anywhere as a consequence of looking at a board. Card triage is the exception, and it is one the developer turns off in a setting: classifying a card sends that card's issue and pull request text to Anthropic's API, because inference is cloud-based — titles, bodies and recent comments, other people's included, and with them every commenter's login, how each relates to the repository, who was asked to review and what each review said. On a private repository that last part is what somebody would object to, so it is named rather than folded into “the card's text”. It is the same trust the developer already extends by running Claude Code on the repository, made on their behalf by a background process rather than by them typing, which is why the setting exists and why the requirement states it (R38).

**Acting is local, and it is the one thing the board does to the developer's code.** A card action runs an agent in their own checkout under the permission mode they chose; nothing about it goes anywhere the developer's own `claude` session would not already go. What it may do is bounded by that mode, by which actions they turned on, and by the ceilings on how many run at once and in a day — and every run is recorded in `actions.json` with what authorised it.

The snapshot is the developer's work in the open: session titles derived from their prompts, the absolute path of every checkout, branch names, issue and pull request titles, and the `gh` logins they declared. `hub.log` carries the same, plus the loop that produced it: which source was read and how long it took, which cards were moved, which cards were read by a model, and which runs were started in a checkout. It also holds the origin of any web page that reached the loopback port and was refused — a slice of browsing history, clipped and rationed, kept because a board that cannot reach its hub has nothing else to go on.

A client is sent none of that file until it asks, and the browser is sent all of it but the origin. That is a deliberate line and not a claim that the rest is already public: the log carries more than the snapshot does — how long each read took, which cards a model was asked about, which runs started in which checkout, the workspace root every client says it has, and every line the hub's own stdout and stderr put there, which is arbitrary output from the CLIs it spawns. What makes it the developer's to see on a page they are already looking at is that all of it is their own machine, and the overlay is a board they opened. The origin is the exception because it is the one thing in the file that is *not* about this machine's work: it is somebody else's page, recorded because a board that cannot reach its hub leaves no other evidence. The bridge takes it out and leaves the refusal, since a page probing the port is the thing worth seeing and which page it was is not the browser's to be told. The overlay paints into github.com, whose own scripts can read what the sidebar writes, so that redaction is the boundary — narrowing what else crosses would mean narrowing the log itself, which is the file a developer opens after a crash. `config.json` carries the settings behind the snapshot: the repository, the logins, and the paths of the CLIs the hub spawns. `triage.json` carries what each card was read to be waiting on, `actions.json` what the board has run on each and what authorised it, `issues.json` the title, status and pull request of every issue the board has read, and `runs/` one file per card holding what a run wrote about itself. All are written for the developer alone, as the bundle is. Any process running as the developer can read `hub.json` and so the snapshot; the token keeps other users and web pages out, not the developer's own processes, and on Windows a file mode is not protection. Nothing else on this list goes anywhere. The Chrome extension keeps the last snapshot in `chrome.storage.session`, which Chrome clears when it exits, and nowhere else.

## 4. Clients

A client renders the snapshot and forwards actions. It holds no state the hub does not, except what its own display needs to draw.

**VS Code board.** The webview panel, the commands, the settings UI, and the resident half of the `vscode` host adapter: it offers every route in `residentRoutes` on `hello`, and performs one with `executeCommand` when the hub forwards it. It is also the client that asks for what the hub `needs`. Everything else it did lives in the hub, the transport included — what stays in the extension is spawning the process and writing the bundle, which are the two things only something inside VS Code can do.

Its surfaces are `--gc-lane` and the footer's tint over `--vscode-editor-background`, which the page and the card both take. The footer mixes `--vscode-foreground` in, so it steps away from the card in whichever direction the theme runs and needs no classification — 4% of it, which is 1.09:1 in Dark Modern and 1.07:1 in Light Modern against GitHub's own 1.09 and 1.07, because the rule above the footer carries the separation and the tint only has to read as a step. The lane mixes *black* in, because it is recessed rather than raised, and that is the one derivation whose size cannot be theme-agnostic — 3% of black is 1.07:1 on white and 1.01:1 on `#1f1f1f`, so the depth is set per theme kind off VS Code's own body class (`mechanics.md` §36). No theme is trusted to separate a card from the editor by fill: Dark Modern puts `editorWidget.background` 1.01:1 from `editor.background`, which is why the card carries `--gc-edge`. A lane is 21.875rem wide, which is GitHub's own 350px column (`mechanics.md` §27) at a 16px root, so a card is the same size on either board. Its pills take GitHub's own label recipe from `mechanics.md` §37 — 20px tall on an 18px line box, the colour at 18% edged with 30% — and the height is pinned there rather than left to font metrics, because `.link`'s 24px click target otherwise made a clickable chip stand taller than a plain one. Its card draws GitHub's own facts above and the board's own below, on a tinted footer reaching the card's three edges — the split the overlay makes on GitHub's card, so one card reads the same on either board. Every footer row is one line, and the whole of it is the control where the session can be opened — the overlay's own shape, and what lets a hover paint the row rather than the words in it. A session's state is `.dot` at its head, taking its colour from `--gc-dot` per phase — reassigned to the card's own attention colour on the row that mark is about, so the card's edge and the row's mark are one colour and the row's words carry nothing, and R6 needs no chip of its own — and its fill from whether the agent still has the session open, and the words at the right are the duration alone — which is what let the saved-session row, the one that used to wrap for a clause naming itself, take the same shape as the rest. Under forced colours the hue is what goes, so the fill is the whole of the distinction there. The name takes `--vscode-foreground` where the row takes `--vscode-descriptionForeground`, and the shimmer's peak is set off the theme-kind body class rather than derived: it is the end of the range the theme runs to, which is white in one direction and black in the other. Its trough is 45% of the way to `--vscode-descriptionForeground` — the overlay's own mix, in VS Code's pair — because a trough on the name's own colour left the pass of light nowhere to travel from and the band read as barely lit. The overlay reaches the same two tones out of Primer's own pair and reads the scheme off GitHub's `data-color-mode` (`mechanics.md` §38). The reading's own row carries the action, how long the card has held its status, and a control: that age is `issue.statusChangedAt` rather than the reading's own `at`, ticking on the same one-second clock the durations run on and carrying the same `data-gc-since` they do — one attribute for every age either board draws, so one pass advances them all and each writes into the text node it already has rather than over it, and the sentence the reading produced — with when it was read — is the chip's tooltip rather than a paragraph under it. The chip is a `span` again with a `button.triage-again` inside it, because a chip whose words are worth clicking to read in full must not spend the developer's usage when they do. That button and the age share one grid cell in `.triage-end`, so the chip measures the same whichever is showing, and the button is `visibility: hidden` rather than transparent — the two overlap, and a control nobody can see must not be one the pointer can still press. It appears on `.badge.triage:hover` — the chip's own hover, not the card's, so a pointer crossing a lane swaps the age for a control on nothing it passes — and on `.card:focus-within`, which works because the card itself carries `tabIndex = 0`: the keyboard reaches the card, the control becomes visible, and the next tab lands on it. The `⋯` menu is `position: fixed` on the document body rather than inside the card, since a lane scrolls its own cards and would clip one. One control, `wireMenuControl`, serves both the cards and the board's own header menu; a header control is never rebuilt, and its items are fetched at the moment of opening because each toggle among them carries the state it had then. Whether the archive is shown is a variable in the script rather than a checkbox in the header it used to be, so a menu built on demand reads it. `setState` carries it across a webview reload, and the extension keeps the standing choice in `globalState` under `groundControl.showArchived` — the webview's state dies with the tab, and this outlives it. The toggle posts `setShowArchived`, and the `ready` a board posts once per run is answered with `showArchived` alongside the log state. A draw with nothing archived clears the variable without writing that back: an archive that emptied is not the developer changing their mind. Being fixed is also why a scroll or a resize closes it: the lanes move under it and it does not follow. It is re-anchored on every draw, because a snapshot that rebuilds a card takes the control the menu was hanging from with it, and it re-anchors on the element rather than on the card being in the snapshot — the board keeps the element of a card the archive toggle is hiding, and a menu measured against one of those parks itself in the corner.

**The editor's log viewer (R40).** Two of VS Code's own output channels rather than a pane the board builds: **Ground Control** for what this window is doing and **Ground Control Hub** for what the background process is. The editor already gives them a level picker, a filter box, scroll-lock and a Copy — and a viewer inside the webview would be the board's second panel, one that reflows the lanes to make room for it. The board's own channel is a `LogOutputChannel`, so VS Code stamps and levels every line and its log-level setting filters them; the hub's is a plain one, carrying the lines of `hub.log` verbatim — including the ones no logger wrote, which arrive scoped `raw` and are written as themselves rather than given a timestamp and a level they never had. That asymmetry is the timestamps: a `LogOutputChannel` stamps each line with the moment it arrived, and the tail a viewer opens with was written minutes or hours ago — restamping it would date a crash to the moment the developer went looking for it.

Whether the hub's log is arriving is the client's to hold, not any board's: the toggle has to survive a board closing and has to be the same answer in a window where the command was used with no board open. So the client owns the flag, sends `watchLog`, and fires an event the board paints from. A checked **Stream hub log** item in the header's own overflow menu toggles it, and `Toggle Hub Log` does the same from the palette — which is also the only way off once the board that turned it on has been closed, since the flag outlives the board on purpose. **Show board log**, an item in the same menu, reveals the other channel and toggles nothing: that one is written whether or not anybody is looking, so there is nothing there to turn off. Turning streaming on reveals the hub's channel; turning it off writes a line saying so and leaves the panel where the developer put it, and entries still in the stream are dropped rather than appended under a line that says nothing more is coming.

The button carries its own state because nothing else can: VS Code exposes no event for an output channel being shown or hidden (`mechanics.md` §34), so a subscribed channel and an unsubscribed one look identical. Its state is pushed on a `ready` the board script posts once per run, not on the panel opening: a webview reloads on its own — a tab returning from the background, a renderer restored — and a button left reading off while the window was streaming would have the developer's first click stop the stream rather than start it.

The subscription is restated after every hello, under the rule §3 sets out. What the restate brings back is the whole tail, so the client writes a line saying the log follows again from the top — a hundred lines repeating themselves with nothing between them reads as the hub looping.

**GitHub project overlay.** A Chrome extension whose content script runs on project board pages, finds the issue number in each card's link, and paints a footer inside the cards the snapshot knows: a first line carrying the lane the board has the card in and R6's returned mark, then one row per session, the full width of the card and one line of it, carrying a `.gc-dot` for the one state the board will claim for it — the phase in its colour, whether the agent still has the session open in its fill — then its agent, its own name, and how long that state has held. Where there is no observation the CLI's own word stands in place of the duration, and where there is neither, nothing. The saved-session row is the same shape, its hollow mark saying what a clause naming it used to. R6's attention is written to GitHub's own card element, which rings the card with a 1px outline — the width the editor board's card border takes — because a footer is not readable at the distance a project board is, and the CSS marks the row that attention is about in the ring's own colour, on the `.gc-dot` at its head and nothing else, rather than adding a badge that says the same thing without naming which session means it. A running session's name carries a pass of light instead, monochrome, because yellow and blue already mean the two things that want the developer. A scan draws only what has changed under it: a `WeakMap` on GitHub's own card node holds each footer and the signature it was drawn from, so a card the snapshot did not move keeps the element it has — the pointer stays on the row it was on, and a running session's pass of light runs on rather than starting again. A view switch replaces the card node (`mechanics.md` §27), which is a miss and rebuilds. The overlay's own menu is kept the same way, by what it draws rather than by its node, so the item under the pointer survives a scan; every popover it opens — a card's lane menu and the board panel alike — is fixed to the viewport and closes on a scroll or a resize, since nothing re-places one between scans. Durations advance in place on a one-second timer rather than through a repaint, and each writes into the text node it already has: `textContent` replaces that node, which is the one kind of change the scan observer answers with a rebuild of the board. The footer goes inside the card's own box rather than under the card element, which is GitHub's drag handle wrapped around it (`mechanics.md` §27). What R25 asks be stated once is split by what the developer must do about it. What went wrong — a source that failed, a hub that cannot be reached, an action refused — is a toast, in front of them and dismissible, and one toast per condition however many times the board repaints. A card's own reading sits on its head line: the action, how long the card has held its status, and the sentence it produced — with when it was read — on hover rather than under it — this board offers no control there, because reading again spends the developer's usage and the bridge takes refresh, watching and move and nothing else. What is merely true of the board as a whole — how old its own reading of the machine is, what a hook install did — is in a menu the overlay hangs in the board's own filter bar, beside GitHub's View button and wearing its classes, because the page has no space above the lanes that is the board's to take. The button carries a mark when the reading is stale, so a bridge that lost the hub never leaves a footer that looks current. Its actions are `refresh`, from that menu, `watchLog`, from the same menu's **Show log** item, a `move` to another lane, offered from the lane chip, and going to a session, which is the row itself: an `<a href="vscode://groundcontrol.ground-control/open?session=…">`, because only a navigation the developer makes in the application in front of them can hand VS Code the foreground. That link is a second entry point into the one open path — the extension's URI handler resolves it to the same `open` the board's own row sends — and it is reachable from any page, so it takes one well-formed session id and nothing else, which the hub then resolves against its own roster and refuses by name. `openable` for a client resident in nothing is the configured host's own answer rather than empty, because the link addresses the editor rather than a window that is running. Stopping a session and taking it over is not offered: the resident half is in VS Code, and the row goes to a session rather than seizing one.

**The overlay's log sidebar (R40).** A panel fixed to the right of the board, over GitHub's columns rather than beside them: making room would reflow the board, and a developer closing the log wants it where they left it. One chronological run of both sources, each line tagged `browser` or `hub` and tickable off by source, sticking to the bottom only when the developer already was there. It opens from a **Show log** item in the menu the overlay already hangs in the filter bar, because a second button next to GitHub's own would cost the board width for something opened rarely. Its ticks are display filters over lines the document keeps, so hiding one is reversible; the detail level starts hidden, for the reason R40 gives.

A click off it closes it, like every other panel here, and closing it stops the hub being read — a developer back on the cards is no longer a viewer. **pin** turns that off, for the case they are watching the log *while* working and will keep the hub read to do it. Pinned needs two guards rather than one: with nothing else open the outside-click handler is not armed at all, but a menu opened over the sidebar arms it for the menu, and the click that dismisses the menu must leave the sidebar alone. The state rides the panel's own edge as well as the tick, because a tick in a row of ticks is not something a developer scans.

The bridge is this board's client, and its own narration has nowhere to be written — so it is relayed to the worker as `browser` lines, from `info` up. The line per message is left out on this side: each one costs a frame across Chrome's port, and the frames themselves are what it would be describing.

It is created once by id, appended to a line at a time, and a scan only reconciles it being open or closed — the same treatment the menu and every unchanged card footer get, and for the same reason: a view switch replaces every card node (`mechanics.md` §27), so what a scan rebuilds is what it no longer recognises rather than everything it finds. Creating it is synchronous with the developer opening it rather than left to the next scan, because what the subscription is answered with arrives before that frame — a panel that did not exist yet would drop the one thing it was opened for. Appending is done with the observer disarmed, the same way painting is — a line is a DOM change of the overlay's own, and an armed observer would schedule a whole board scan per line of a burst.

The subscription is the worker's, not a tab's, and `makeLogSpool` in `state.js` is what decides it: a tab's `logView` moves the spool, and the hub is told only when the first sidebar opens and when the last one closes. A tab opening the second sidebar is handed what the worker already holds instead, because telling the hub again would have it backfill over the first tab's stream. The exceptions are the two restates — the worker's, when its own alarm reopens the native port, and the bridge's, after every hello — and both are answered with the whole tail, so a line saying the file follows again from the top goes above it. The browser's own half is kept whatever a sidebar is doing; the hub's is dropped when the last one closes, because a reopen is answered with a fresh tail and a kept copy would show that history twice. A developer opening the panel after the overlay went quiet gets the lines that led there, as far back as the worker has been alive: Chrome stops an idle one, and its own half goes with it — the cost of holding a log nowhere but in memory. None of it reaches `chrome.storage.session`: the hub's own file is the durable copy, a worker Chrome stopped is answered by the reconnecting tab asking again, and a log is not something to leave lying about in browser storage. Leaving a board closes the sidebar and stops the reading, because a tab on some other page of github.com is not a viewer. The worker restates both what it is watching and what it is reading whenever it opens the native port, not only when a tab connects: the port is reopened by the worker's own alarm after Chrome stopped it, and what comes back is a new bridge process and so a new client of the hub, which knows nothing about this browser.

The content script is injected across `github.com` rather than on project boards alone, because a board reached by clicking through the site is a soft navigation and Chrome injects nothing for one. Which pages it paints is therefore decided in the script, on every location change, and leaving a board is something it handles rather than a page it never sees.

The overlay splits three ways, and the two halves holding no `chrome` port are the ones vitest reaches. `overlay.js` is a pure function of a snapshot and a document; `state.js` is what a message from the worker does to what is drawn, which page is a board, how long to wait before trying the worker again, and whether trying again can mean anything — `disconnection` reads `chrome.runtime.id`, which is undefined in a script the extension's own reload has orphaned (`mechanics.md` §27), and a tab handed that answer stops its observer and both of its interval timers and asks to be reloaded, rather than retrying a runtime whose every call throws. What is left in `content.js` is the port and the observer, and in `worker.js` the native port.

The trouble line is the worker's to set and clear, never the tab's. A tab is handed the last snapshot from `chrome.storage.session` before anything has answered, and a tab that cleared the line on receiving one would show an hours-old reading beside a button saying nothing was wrong (R24). The footer is rebuilt from scratch on every scan rather than patched, because a view switch replaces every card node and takes the footer with it (`mechanics.md` §27) — and the observer is disarmed while painting, or the badges it writes would schedule the next scan forever.

**Worked example.** A hook fires `PermissionRequest` for the Claude session on issue 4521. Claude's activity writer replaces that session's marker. The hub's watcher fires; the session is listed, so the roster is not stale, and the hub reads one file instead of spawning the CLI. `phaseOf` returns `waiting`. The hub rebuilds the snapshot and pushes `changed` to both clients. The VS Code webview repaints the card amber. The bridge relays the message to the worker, the content script finds the project card whose link ends in `/issues/4521`, rings it, and paints that session's row amber with the duration. End to end is one file event plus the 150 ms batch window.

The extension also imports `board` and `github` for the two settings readers that turn a raw value into one the hub takes. Those stay in the client: what they read is VS Code's own settings, which only something inside VS Code can see. The Chrome client has no build step and imports nothing at runtime — `core` reaches it as JSDoc types, so a protocol rename fails its typecheck, and Chrome loads the directory as it stands.

One package per adapter is what makes the seams enforceable. The boundary rule and the coverage floor apply per package, so `agent-claude` cannot reach `host-vscode`, and an adapter that arrives without tests fails on its own number rather than hiding in a larger one. `core` names no adapter; the registries are the hub's.

Configuration names each registry by id, and an unknown id is a named failure on the board rather than a silent omission:

```jsonc
"groundControl.agents": { "claude": "claude", "codex": "codex" },
"groundControl.hosts": ["vscode"],
"groundControl.sources": ["github"]
```

## 6. Adding a target

**A second agent in VS Code.** `packages/agent-codex` is the `codex` adapter, and it is one entry in the registry. Codex has no command that lists live sessions, so its `listSessions` reads the same hook markers its `activity` signal writes, and the pid each marker carries is what proves a session alive (`mechanics.md` §39, §40). It carries `dispatch` and `stopDispatch` — `codex exec` detached, stopped by signalling the pid its own marker names — and `canResume`, which asks whether Codex still holds the rollout rather than whether the saved checkout is still there, because a thread is opened by its id wherever it once ran (§44). It carries no `classify`. Its `enabledByDefault` is the presence of Codex's own home — `$CODEX_HOME`, else `~/.codex` — which is why a roster needs no setting: `listSessions` ignores the path it is handed, so the only thing `groundControl.agents` buys a Codex is a `dispatch` that can find the binary. Trust runs through Codex rather than around it. `trust.ts` derives the keys Codex would name the board's entries by — from where each entry actually sits in `hooks.json`, since a hook of the developer's own shifts the board's along — and reads which carry a `trusted_hash` in `config.toml`. Where any do not, `exchange.ts` drives `codex app-server` — `initialize`, then `hooks/list` for each entry's `currentHash`, then one `config/batchWrite` upserting the `hooks.state` table — so Codex writes its own file and the board computes no hash and edits no TOML (§41). That split is what makes the conversation testable: `exchange.ts` decides what to send from each reply and holds every way it can end, and `appServer.ts` only spawns and moves bytes. It filters to entries whose command is exactly the writer it installed, which is what keeps the grant to its own hooks. The exchange spawns a process, so it is never awaited by a roster read: the read that starts it reports nothing, the attempt is remembered against the set of untrusted keys so a reinstall is retried and a refusal is not, and the next read reports whatever stopped it.

**The board's permission modes are translated, not passed through.** Codex has two controls where Claude has one — a sandbox and an approval policy — so the adapter maps `plan`, `dontAsk` and `bypassPermissions` onto them and refuses `manual`, `auto` and `acceptEdits` by name: `codex exec` has nobody to answer an approval, so a run under one of those would start, fail its first tool, and report work it never did. `dontAsk` also carries `sandbox_workspace_write.network_access=true`, because `workspace-write` blocks outbound sockets and the merge action ends in a push (`mechanics.md` §46); `plan` keeps no network, as a plan does not push.

**A second host.** A `packages/host-windows-terminal` implements `windows()` over the terminal's own window enumeration and an `open` that brings a window forward. It has no resident half, so `residentRoutes` is empty and `plan` only ever returns focus routes. One string in the hosts list.

**A second work source.** A `packages/source-factory` reads `.factory/*/state.json` and reports each item's station. The lane rules gain the station-to-lane mapping. One string in the sources list.

## 7. What each layer owes in tests

The contract is `testing.md`; this is where each layer lands in it.

- `core` earns tests for its helpers, the paths, the branch link, the CLI runner, the disk readers, and none for its types.
- Each adapter tests its parsing, its failure classification, and its refusals against recorded, scrubbed fixtures. A script an adapter hands to its CLI, such as Claude's activity writer, is tested by spawning it.
- `hub` tests the loop with an injected clock and fake adapters: coalescing, staleness, idle-when-unwatched, lane memory round trips, the watcher over a temp directory, and the server's refusals against a fake hub.
- `apps/hub` has no coverage floor; its entry point is covered by a test that spawns the built bundle with an empty home and reads what it serves.
- Each client's DOM layer imports nothing from its platform and tests under jsdom with payloads built from `core`'s types. The Chrome overlay's card matching runs against recorded project board markup, which is version-fragile and dated in `mechanics.md` like every other undocumented surface.
